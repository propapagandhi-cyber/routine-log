## Context（背景・前提）

- ADR-0002 では「`piano-log` がすでに Google スプレッドシートを使っている」ことを理由に、そこへ合わせた。
  しかし確認すると、`piano-log` の保存先は一度も設定されておらず、スプレッドシートは存在しなかった（記録は iPad の中だけ）。
- 同じ家族向けの「おうちカレンダー」は、GitHub の非公開リポジトリの JSON ＋ 接続コードの方式で動いており、
  実際の GitHub への同期も確認ずみ。
- 家族の端末に Google アカウントでログインさせたくない。保存場所を 2種類に分ける利点は見当たらない。
- `piano-log` 側を変更してよい、という前提をもらっている。

## Decision（決めたこと）

1. **記録は、GitHub の非公開リポジトリ（データ用。既定の名前は `Routine-data`）に JSON で置く。**
   ブラウザから GitHub REST API（git trees／blobs と Contents API）で読み書きする。
2. **習慣きろくと `piano-log` は同じデータ用リポジトリを使う。** ファイルを分ける：
   `routine/config.json`、`routine/<人>/<年>.json`、`piano/settings.json`、`piano/records-<年>.json`。
   習慣きろくはピアノのファイルを読むだけ、`piano-log` は習慣のファイルに触れない。
3. **認証は fine-grained personal access token**（対象はデータ用リポジトリだけ、権限は Contents の読み書きだけ）。
   ユーザー名・リポジトリ名・トークンを「接続コード」（`KIROKU1:…`）にまとめ、各端末に 1回貼る（設定用リンクでも可）。
   接続コードは端末の localStorage にだけ保存する。両アプリで同じ接続コードを使う。
4. **書き込みは「読む → 記録単位でマージ → sha 付きで書く」。** 競合したら読み直してやり直す。
   習慣の記録は更新日時が新しい方、ピアノの記録は ID 単位の追加・削除。
5. **読み込みは、ファイルの一覧（sha）を見て、変わったファイルだけ読む。**
6. `ghstore.js`（GitHub とのやりとり・接続コード・ファイルの形）は両アプリで同じ内容にする。正は本リポジトリ。
7. アプリ本体は別の公開リポジトリのまま（ADR-0002 の「アプリは別にする」は引き継ぐ）。

## Consequences（結果・トレードオフ）

- 家族向けアプリの保存方式がそろう。Google の設定（Apps Script のデプロイ、権限の許可）がいらない。
- 変更のたびにコミットが残るので、誤操作しても履歴から戻せる。
- トークンはデータ用リポジトリ限定で、無効化できる。端末をなくしたらトークンを消す。
- トークンに期限がある場合、切れると同期が止まる。画面に案内を出し、作り直して接続コードを配り直す。
- 表計算ソフトで直接は見られない（GitHub の画面で JSON として読める。1日 1行）。
- 1回の保存で、その人のその年のファイル（1年で 100KB ほど）をまるごと送る。数回のタップは 1回の書き込みにまとめる。
- 接続コードを知っている人は、データ用リポジトリを読み書きできる。

## Alternatives（検討した他案）

- **Google スプレッドシート＋Apps Script（ADR-0002）**：合わせる相手が実在しなかった。URL を知る人は誰でも読み書きでき、
  止めるには再デプロイが要る。表計算で見られる利点はあるが、手入力のシートをやめるのが目的なので弱い。
- **おうちカレンダーのデータ用リポジトリに同居**：使う人と端末が違う（カレンダーはママのスマホが中心）。
  接続コードを分けておけば、片方の端末をなくしても影響がもう片方に及ばない。
- **1つのファイルに全部入れる**：数年で 1MB を超え、1タップごとの送信が重くなる。人 × 年で分けた。
